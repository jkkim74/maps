제목: [AI 블로그 자동화 #2] AI에게 DB를 주지 않았습니다, 하루치 JSON을 먼저 만드는 이유

안녕하세요 :)

1편에서 "AI가 DB를 직접 보게 하지 않는다"는 원칙을 이야기했습니다.
이번 편은 그 원칙을 코드로 만든 1단계, 다이제스트입니다.

다이제스트는 하루치 매매 기록을 담은 JSON 파일 하나입니다.
파이썬이 DB에서 결정적으로 조립하고, AI는 이 파일만 읽습니다.
글에 나오는 숫자와 사유는 전부 여기서 옵니다.


────────────────────
1. 파일 하나에 뭐가 들어가나
────────────────────

9월 4일자 다이제스트의 최상위 키입니다.

  ref_date                    2026-09-04
  generated_at                2026-09-04T09:30:04+00:00
  market                      시장 국면, 팩터 5개, 신규매수 한도
  sectors                     강세 업종 5개 (관측 전용)
  strategies                  전략 8개의 활성 여부와 차단 사유
  candidates                  완성 점수가 있는 후보 상위 12개
  incomplete_candidates       점수 계산이 덜 된 후보 12개
  candidate_total             317
  candidate_ready_total       204
  candidate_incomplete_total  113
  portfolio                   계좌 총액, 현금, 보유 종목별 평가손익
  tomorrow_orders             내일 아침 주문 예정 목록
  conditional_entries         사람이 무장한 분할 진입 상태
  executions                  오늘 체결 2건
  market_context              외부 리포트 발췌 4건
  errors                      [] (비어 있음)

파일 크기는 날마다 다르지만 대개 60~90KB입니다.
AI 입장에서는 4만 토큰쯤 되는 입력입니다.

market 섹션의 앞부분만 잘라 보면 이렇습니다.

  "market": {
    "regime": "mixed",
    "raw_regime": "mixed",

    "entry_limit_ratio": 0.0,

    "up_count": 6,

키 이름이 곧 글쓰기 프롬프트의 어휘가 됩니다.
3편에서 보시겠지만 프롬프트는 "entry_limit_ratio를 쉬운 문장으로 풀어라" 식으로
이 키 이름을 그대로 부릅니다. 그래서 키 이름을 한 번 정하면 잘 안 바꿉니다.


────────────────────
2. 스키마를 먼저 고정한다
────────────────────

Pydantic 모델로 스키마를 먼저 박았습니다.
FastAPI를 쓰고 있어서 응답 모델로도 그대로 쓰입니다.

▶ 파일: maps/api/schemas.py (발췌)

  class DigestFactor(BaseModel):
      """시장 팩터 1개. measured=False면 실제 데이터가 없어
      중립값(50)이 들어간 것이다."""
      name: str
      score: float | None = None
      measured: bool = True
      note: str | None = None
      source: str | None = None


  class DigestExecution(BaseModel):
      order_id: str
      strategy_id: str | None = None
      ticker: str
      name: str | None = None
      side: str
      qty: int
      order_price: float | None = None
      fill_price: float | None = None
      fill_qty: int = 0
      status: str
      exit_reason: str | None = None      # 매도만. 없으면 컬럼 도입 전 기록
      created_at: str
      entry_rationale: str | None = None  # 매수 시 후보 점수의 근거 문장
      ai_recommendation: str | None = None
      decision_context: dict[str, Any] | None = None
      warnings: list[str] = []


  class DailyDigest(BaseModel):
      ref_date: str
      generated_at: str
      market: DigestMarket | None = None
      sectors: DigestSectors | None = None
      strategies: list[DigestStrategy] = []
      candidates: list[DigestCandidate] = []
      incomplete_candidates: list[DigestCandidate] = []
      candidate_total: int = 0
      candidate_ready_total: int = 0
      candidate_incomplete_total: int = 0
      portfolio: DigestPortfolio | None = None
      tomorrow_orders: OrderPreviewResponse | None = None
      conditional_entries: list[DigestConditionalEntry] = []
      executions: list[DigestExecution] = []
      market_context: list[DigestReportExcerpt] = []
      errors: list[str] = []

여기서 제가 제일 공들인 필드가 measured 입니다.


────────────────────
3. "미측정"이라는 값을 따로 둔 이유
────────────────────

시장 점수는 팩터 5개의 가중 합입니다.
가격 추세, 변동성, 유동성, 외국인·환율, 투자심리.

그런데 7월 말 시점에 유동성과 투자심리 피드는 아직 연결이 안 돼 있었습니다.
코드는 그 자리에 중립값 50을 넣고 돌아갔습니다.

첫날 다이제스트에 이 50이 그냥 숫자로 들어갔습니다.
AI가 뭐라고 썼을까요.

  "투자심리 점수 50.0으로 중립 수준을 유지했다"

없는 분석을 지어낸 겁니다. 데이터가 없는 건데 "중립을 유지"했다고 썼습니다.
AI 잘못이 아닙니다. 50이라는 숫자만 보면 그렇게 읽는 게 당연합니다.

그래서 팩터마다 measured 플래그를 달았습니다.
실측이 아니면 measured=false 로 내려보내고, 프롬프트에서는
"measured가 false면 미측정이라고만 적어라, 점수를 인용하지 마라"고 못 박았습니다.

▶ 파일: maps/ops/daily_digest.py (발췌)

  # 어떤 팩터가 실측인지는 provider 종류로 판정한다.
  # 하드코딩하지 않아야 실제 피드가 붙는 날 자동으로 True가 된다.
  unmeasured_note = "매크로·수급·센티먼트 피드 미연결, 중립값(50) 자리표시자"
  placeholder = type(analyzer._kostolany_provider) is PlaceholderKostolanyDataProvider
  factors = [
      DigestFactor(name="price_trend", score=composite.price_trend_score),
      DigestFactor(name="volatility",  score=composite.volatility_score),
      DigestFactor(name="foreign_fx",  score=composite.foreign_fx_score),
      DigestFactor(
          name="liquidity",
          score=composite.liquidity_score,
          measured=not placeholder,
          note=None if not placeholder else unmeasured_note,
      ),
      DigestFactor(
          name="psychology",
          score=composite.psychology_score,
          measured=not placeholder,
          note=None if not placeholder else unmeasured_note,
      ),
  ]

7월 27일자 글은 그래서 이렇게 나갔습니다.

  미측정 팩터: liquidity, psychology

지금은 두 피드가 다 붙어서 9월 다이제스트는 measured_factors 5개, missing 0개입니다.
코드는 안 고쳤습니다. provider가 바뀌니 플래그가 저절로 뒤집혔습니다.


────────────────────
4. 섹션 하나가 죽어도 나머지는 나온다
────────────────────

시장 국면 섹션은 외부 API(pykrx, yfinance)를 탑니다. 실패가 드물지 않습니다.
그런데 그것 때문에 체결 기록까지 통째로 날아가면 그날 기록이 사라집니다.

그래서 섹션마다 따로 감쌌습니다.

▶ 파일: maps/ops/daily_digest.py

  def build_daily_digest(db, settings, ref_date) -> DailyDigest:
      digest = DailyDigest(
          ref_date=ref_date.isoformat(),
          generated_at=dt.datetime.now(dt.timezone.utc).isoformat(),
      )

      def _section(name, fn):
          try:
              return fn()
          except Exception as exc:
              logger.warning("다이제스트 섹션 실패 [%s]: %s", name, exc)
              digest.errors.append(f"{name}: {exc}")
              return None

      digest.market     = _section("market",     lambda: _build_market(db, settings, ref_date))
      digest.sectors    = _section("sectors",    lambda: _build_sectors(db, settings, ref_date))
      digest.strategies = _section("strategies", lambda: _build_strategies(db, settings, ref_date)) or []
      digest.portfolio  = _section("portfolio",  lambda: _build_portfolio(db, ref_date))
      digest.executions = _section("executions", lambda: _build_executions(db, ref_date)) or []
      digest.market_context = _section("market_context", lambda: _build_market_context(db, ref_date)) or []
      return digest

실패한 섹션은 None이 되고 사유가 errors 배열에 쌓입니다.
프롬프트 쪽 규칙은 "errors가 비어 있지 않으면 해당 섹션을 수집 실패로 명시하라"입니다.

이 구조 덕에 AI는 "데이터가 없다"와 "수집이 실패했다"를 구분해서 씁니다.
둘 다 추정치로 메우지 않습니다.


────────────────────
5. 첫 주에 잡힌 버그 두 개
────────────────────

다이제스트를 만들다 보니 매매 시스템 자체의 구멍이 보였습니다.
글을 쓰려니 데이터가 없다는 걸 그제야 안 겁니다.

▶ 매도 사유가 DB에 없었다

첫날 체결 섹션을 만드는데, 왜 팔았는지가 order_log 어디에도 없었습니다.
손절인지 익절인지는 서버 로그(journald)에만 찍히고 있었습니다.
로그는 며칠 지나면 돌아가며 지워집니다.

exit_reason 컬럼을 추가하고 청산 경로 두 곳(손절, 브래킷)에서 채우게 고쳤습니다.
마이그레이션 0012번입니다.
이게 없었으면 "매도 이유가 기록되지 않았습니다"라는 문장이 매일 나갈 뻔했습니다.

▶ 아침 주문이 전날 기록으로 빠졌다

주문은 08:55 KST에 나갑니다. DB에는 UTC로 저장됩니다.
UTC로 08:55 KST는 전날 23:55입니다.

날짜만으로 "오늘 주문"을 조회하니 아침 매수가 통째로 조회 범위 밖으로 빠졌습니다.
7월 27일 SK이터닉스 매수가 그렇게 사라졌다가 잡혔습니다.

▶ 파일: maps/execution/order_manager.py

  def kst_day_bounds_utc(ref_date: date) -> tuple[datetime, datetime]:
      """KST 하루(00:00~24:00)를 order_log.created_at 과 같은
      UTC naive 구간으로 반환한다. 08:55 KST 주문은 UTC로 전일 23:55다."""
      start = datetime.combine(ref_date, dt_time.min) - timedelta(hours=9)
      return start, start + timedelta(days=1)

체결 조회는 전부 이 함수를 거칩니다.

  def _build_executions(db, ref_date):
      start, end = kst_day_bounds_utc(ref_date)
      rows = (
          db.query(OrderLog)
          .filter(OrderLog.created_at >= start, OrderLog.created_at < end)
          .order_by(OrderLog.id)
          .all()
      )


────────────────────
6. 나중에 덧붙인 것들
────────────────────

두 달 운영하면서 스키마가 세 번 커졌습니다. 전부 글을 읽다가 생긴 요구입니다.

▶ 주문 순간의 근거 (8월 25일)

다이제스트는 저녁에 만듭니다. 그때의 시장 국면은 장 마감 시점 값입니다.
그런데 주문은 아침에 나갔습니다. 아침의 판단 근거와 저녁의 시장 상태를 섞어 쓰면
"왜 샀나"가 틀립니다.

그래서 주문할 때 판단 근거를 order_log.decision_context 에 JSON으로 박아 두고,
다이제스트는 그걸 우선 씁니다. 옛날 주문처럼 그게 없으면 과거 후보 점수에서 추론하되
warnings 에 DECISION_CONTEXT_INFERRED 를 달아 보냅니다.

  warnings: list[str] = []
  if row.side == "buy" and pick is None and row.decision_context is None:
      warnings.append("DECISION_CONTEXT_INFERRED")

프롬프트는 이 경고를 보면 "추론한 값"이라고 명시하고 확정 사실처럼 쓰지 않습니다.

▶ 데이터 미완성 후보 분리 (8월 27일)

후보 점수는 여러 항목의 합인데, 일부 항목이 아직 안 채워진 종목이 섞여 있었습니다.
그 부분 점수가 완성 점수와 같은 순위표에 놓이니 글에서 "상위 후보"로 둔갑했습니다.

candidates 와 incomplete_candidates 를 갈랐습니다.
후자에는 score_coverage_ratio 와 missing_components 를 같이 실어서
AI가 "부분 산출값, 순위 비교 금지"라고 쓰게 했습니다.

▶ 계좌와 보유 종목 (8월 하순)

처음엔 portfolio 섹션이 없었습니다.
7종목 2천만 원을 들고 있는데 매매 기록 어디에도 안 나오더군요.
portfolio_snapshot 테이블에서 총액·현금·종목별 평가손익을 붙였습니다.


────────────────────
7. 실행 방법
────────────────────

배치 스크립트에서는 파이썬 한 줄로 부릅니다.

  python -c "
  import datetime, json, sys
  from maps.common.db import SessionLocal
  from maps.common.settings import get_settings
  from maps.ops.daily_digest import build_daily_digest

  ref = datetime.date.fromisoformat('2026-09-04')
  db = SessionLocal()
  try:
      digest = build_daily_digest(db, get_settings(), ref)
  finally:
      db.close()
  with open('/opt/maps/logs/digest_2026-09-04.json', 'w', encoding='utf-8') as fh:
      json.dump(digest.model_dump(), fh, ensure_ascii=False, indent=2, default=str)
  for err in digest.errors:
      print(f'  [섹션 실패] {err}', file=sys.stderr)
  print(f'  후보={digest.candidate_total} 체결={len(digest.executions)} 오류={len(digest.errors)}')
  "

ensure_ascii=False 를 빼먹으면 한글 종목명이 전부 \uXXXX 로 들어갑니다.
AI는 그것도 읽긴 하는데 토큰이 세 배로 늘어납니다.

디버깅용으로 같은 함수를 API로도 열어 뒀습니다.

▶ 파일: maps/api/daily_digest.py

  router = APIRouter(prefix="/api/v1/daily-digest", tags=["Daily Digest"])

  @router.get("", response_model=DailyDigest)
  def get_daily_digest(date: str | None = Query(default=None), db: Session = Depends(get_db)):
      ref_date = dt.date.today() if date is None else dt.date.fromisoformat(date)
      return build_daily_digest(db, get_settings(), ref_date)

브라우저에서 /api/v1/daily-digest?date=2026-09-04 를 열면 배치가 볼 것과
똑같은 JSON이 나옵니다. 글이 이상하면 먼저 여기부터 봅니다.
JSON이 맞으면 프롬프트 문제고, JSON이 틀리면 코드 문제입니다.
책임 소재가 갈리는 게 이 구조의 큰 장점입니다.


────────────────────
8. 정리
────────────────────

다이제스트 만드는 데 하루, 그 뒤로 두 달 동안 조금씩 키웠습니다.
새 계산 로직은 하나도 안 만들었습니다. 매매 시스템이 이미 쓰는 함수를 다시 불렀을 뿐입니다.
그래야 글에 나오는 숫자와 실제 주문에 쓰인 숫자가 같은 코드에서 나옵니다.

다음 편은 2단계입니다.
이 JSON을 읽고 글을 쓰는 프롬프트 전문과, AI의 도구를 막았다고 생각했는데
안 막혀 있었던 이야기입니다.


────────────────────
투자 유의사항
────────────────────

이 시리즈에 나오는 매매 기록은 KIS 모의투자 계좌의 운용 결과이며 실제 자금 운용이 아닙니다.
특정 종목의 매수·매도를 권유하지 않습니다.
투자 판단과 결과의 책임은 투자자 본인에게 있습니다.
