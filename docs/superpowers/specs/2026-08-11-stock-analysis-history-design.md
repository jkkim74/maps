# 종목분석 이력·현재가 갱신·전략매매 연결 설계

## 1. 목표

종목분석 결과를 화면의 임시 상태가 아니라 서버 DB의 이력으로 보존한다. 사용자가 다른 메뉴로
이동했다 돌아와도 과거 분석 목록과 상세 내용을 다시 열 수 있어야 한다. 같은 종목을 재분석하면
기존 결과를 덮어쓰지 않고 새 이력 1건을 추가한다.

과거 상세를 열 때는 분석 당시의 기술지표·재무정보·AI 원고·매매계획을 그대로 유지하고,
현재가처럼 시의성이 높은 값만 별도로 다시 조회하여 보여준다. 저장된 상세의 `매매 설정`에서는
해당 분석 이력의 구조화된 매수가·목표가·손절가를 그대로 사용해 전략매매를 시험할 수 있다.

함께 해결할 기존 UX 결함은 다음 두 가지다.

- 3분할매매 선택 시 숨겨졌던 필드가 4열 자동 그리드에 삽입되며 입력 줄이 어긋나는 문제
- 안전 최대금액을 모르는 사용자가 총 매수금액을 먼저 추측해서 입력해야 하는 역순 흐름

## 2. 범위와 비범위

### 범위

- 분석 완료마다 독립된 이력 행 추가
- 최신순 이력 목록과 저장된 상세 열람
- 상세 열람 직후 현재가 오버레이 자동 갱신
- 현재가와 저장된 진입가·목표가·손절가의 거리 계산
- 이력 상세에서 기존 전략매매 설정 팝업 연결
- 재분석 시 새 이력 추가
- 단일/3분할 입력 필드의 안정적인 행 배치
- 매매 방식 선택 후 안전 최대금액 선계산·총 매수금액 자동 입력
- 최종 무장 시 기존 서버 안전검증 재실행

### 비범위

- 분석 이력 수정·삭제·즐겨찾기·태그
- 이력 보관 기간이나 자동 삭제 정책
- 과거 기술지표·재무정보·AI 원고의 부분 재계산
- 가격 갱신만으로 매수가·목표가·손절가를 다시 생성하는 기능
- 모바일 앱의 분석 이력 작성 UI
- 실거래에서 재분석을 강제로 요구하는 신규 정책

## 3. 선택한 접근

### 채택: 별도 `stock_analysis_history` 저장소와 현재가 오버레이

전체 분석 스냅샷과 AI 원고, 구조화 매매계획을 전용 테이블에 보관한다. 분석 원본 필드는
생성 후 바꾸지 않고, 마지막 조회 가격과 조회 시각만 별도 열에 갱신한다. `AnalysisPick`은
전략매매의 WATCH/ARMED/BOUGHT 상태 저장소로 계속 사용한다.

이 구조는 다음 책임을 분리한다.

- `StockAnalysisHistory`: 사용자가 실행한 분석의 감사 가능한 원본 이력
- `AnalysisPick`: 사용자가 최종 승인한 전략매매 계획과 주문 상태
- 현재가 오버레이: 과거 분석을 바꾸지 않는 일시적·시의성 정보

### 기각: `AnalysisPick` 확장

`AnalysisPick`은 활성 종목 중복 제한, 분할 회차, 주문 ID, 체결 상태를 가진 실행 모델이다.
같은 종목의 반복 분석과 아직 매매하지 않은 상세 이력을 함께 넣으면 조회 의미와 상태 전이가
섞인다.

### 기각: 브라우저 저장소

화면 이동은 버틸 수 있지만 브라우저·기기 변경, 캐시 삭제, 운영 서버 재기동과 무관한 로컬
상태가 된다. 사용자 요청인 history성 보관과 서버 감사 가능성을 충족하지 않는다.

## 4. 데이터 모델

신규 SQLAlchemy 모델 `StockAnalysisHistory`와 Alembic revision
`0022_stock_analysis_history`를 추가한다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `id` | integer PK | 분석 이력 식별자 |
| `created_at` | UTC datetime | 전체 분석 완료·저장 시각 |
| `ticker` | string(16), index | 6자리 종목코드 |
| `name` | string(128) | 분석 당시 종목명 |
| `market` | string(16), nullable | KOSPI/KOSDAQ |
| `ref_date` | date, index | 기술분석 데이터 기준일 |
| `snapshot` | JSON, not null | `analyze()`가 만든 전체 구조화 결과 |
| `narrative` | text, not null | 화면에 표시된 AI 종합분석 원고. AI 실패 시 오류 표식을 포함할 수 있음 |
| `trade_plan` | JSON, not null | 분석과 팝업이 공유하는 구조화 매매계획 또는 MANUAL_REQUIRED 응답 |
| `recommendation` | string(16), nullable | 목록 표시용 BUY/WATCH/SELL 비정규화 값 |
| `analyzed_price` | float, nullable | 목록 표시용 분석 당시 현재가 |
| `latest_price` | float, nullable | 마지막으로 조회한 현재가 |
| `latest_reference_close` | float, nullable | 등락 계산에 사용한 최근 기준 종가 |
| `latest_price_source` | string(32), nullable | broker 또는 historical_ohlcv |
| `price_refreshed_at` | UTC datetime, nullable | 현재가 확인 시각 |

같은 종목·같은 날짜에도 고유 제약을 두지 않는다. 사용자가 전체 분석을 다시 실행할 때마다
새 행을 추가해야 하기 때문이다. 기본 목록 성능을 위해 `(created_at, id)` 최신순과 `ticker`를
조회할 수 있게 한다.

`snapshot`, `narrative`, `trade_plan`, `recommendation`, `analyzed_price`는 생성 이후 수정하지
않는다. 가격 갱신 API는 `latest_*`와 `price_refreshed_at`만 변경한다.

## 5. 저장 흐름

### SSE 전체 분석

1. 기존 `analyze()`가 구조화 분석 결과를 만든다.
2. 기존 `generate_trade_plan()`이 단일 구조화 매매계획을 만든다.
3. Bedrock 원고 스트림의 chunk를 사용자에게 전송하면서 서버에서도 문자열로 누적한다.
4. 원고 스트림이 끝나면 한 DB 트랜잭션으로 `StockAnalysisHistory` 1건을 저장한다.
5. SSE 완료 이벤트에 기존 `data`, `trade_plan`과 함께 `history_id`를 넣는다.
6. 프런트는 완료 후 이력 목록을 다시 조회한다.

AI 원고 생성이 실패해도 구조화 분석은 저장한다. `narrative`에는 사용자에게 이미 보낸 오류
표식을 보존한다. DB 저장만 실패하면 현재 분석 결과는 화면에 보여주되 완료 이벤트에
`history_error`를 넣고 이력 저장 실패를 명확히 표시한다. 저장 실패를 성공처럼 숨기지 않는다.

### 단일 응답 분석 API

`POST /api/v1/stock-analysis/analyze`도 성공한 전체 분석을 동일한 저장 서비스에 전달한다.
원고 스트리밍을 사용하지 않으므로 `narrative`는 빈 문자열이고, 구조화 `trade_plan`은 동일하게
생성한다. 웹 기본 경로는 계속 SSE를 사용한다.

### 재분석

목록 또는 상세의 `재분석` 버튼은 종목코드를 검색 입력에 넣고 기존 SSE 전체 분석을 실행한다.
기존 행을 업데이트하는 별도 재분석 API는 만들지 않는다. 완료 시 항상 새 행이 추가된다.

## 6. 조회와 현재가 갱신 API

### 목록

`GET /api/v1/stock-analysis/history?limit=50&offset=0`

- `(created_at DESC, id DESC)` 최신순
- 기본 50건, 최대 200건
- 목록에는 대용량 `snapshot`과 `narrative`를 제외한다.
- ID, 분석 시각, 종목, 기준일, 의견, 분석 당시 가격, 마지막 현재가와 갱신 시각을 반환한다.

### 저장된 상세

`GET /api/v1/stock-analysis/history/{history_id}`

- 저장된 `snapshot`, `narrative`, `trade_plan`과 마지막 가격 오버레이를 반환한다.
- 읽기 API는 분석 원본이나 가격 열을 변경하지 않는다.
- 없는 ID는 404를 반환한다.

### 가격만 갱신

`POST /api/v1/stock-analysis/history/{history_id}/refresh-price`

- KIS/설정된 브로커의 임의 종목 현재가 조회를 우선 사용한다.
- 브로커 시세가 없으면 DB의 최신 `HistoricalOHLCV.close`를 사용한다.
- 기준 종가가 있으면 현재가 대비 등락 금액과 등락률을 계산한다.
- 저장된 1차 매수가, 목표가, 손절가까지의 금액·퍼센트 거리를 응답에서 계산한다.
- DB에서는 `latest_*`, `price_refreshed_at`만 갱신한다.
- 두 소스 모두 가격이 없으면 503을 반환하고 기존 행은 변경하지 않는다.

상세를 열면 먼저 GET 결과로 저장된 분석을 즉시 렌더링하고, 이어서 가격 갱신 POST를
비동기로 호출한다. 가격 조회 실패는 상세 열람을 막지 않는다. 화면에는 `현재가 갱신 실패 ·
마지막 확인값`을 표시한다.

## 7. 종목분석 화면

검색창 아래, 상세 분석 패널 위에 `분석 이력` 목록을 둔다. 독립 종목분석 화면에서만
목록을 표시하고, 기존 분석 워치 모달에는 중복 목록을 넣지 않는다.

목록 열은 다음으로 제한한다.

- 분석 시각
- 종목명·코드
- 분석 의견
- 분석 당시 가격
- 현재 가격
- 가격 확인 시각
- `상세`, `재분석`

같은 종목의 여러 행을 합치지 않는다. 새 분석이 생기면 가장 위에 별도 행으로 나타난다.
초기 범위에서는 삭제·필터·검색·무한 스크롤을 추가하지 않는다.

`상세`를 누르면 저장된 스냅샷을 기존 `renderResult()` 경로로 표시하고 저장된 원고와
`trade_plan`을 복원한다. 화면 상단에는 다음 시점을 구분해 표시한다.

- `분석 기준`: 이력 생성 시각과 기술 데이터 기준일
- `현재가 확인`: 가격 출처와 갱신 시각

현재가 오버레이는 저장된 차트, RSI, MACD, 이동평균, 재무정보, AI 원고, 구조화 매매계획을
덮어쓰지 않는다. `매매 설정` 버튼은 복원된 `trade_plan`을 사용한다.

## 8. 전략매매 팝업 UX

### 입력 정렬

현재 하나의 4열 자동 그리드를 다음 두 그룹으로 나눈다.

- 공통 행: 시장 / 총 매수금액 / 목표가 / 손절가
- 진입가 행: 1차 / 2차 / 3차 진입가

단일매매에서는 진입가 행에 1차만 표시한다. 3분할매매에서는 세 칸이 같은 행과 폭으로
표시된다. 모바일에서는 각 그룹을 1열 또는 2열로 축소한다. 숨김 필드가 공통 행의 위치를
바꾸지 않게 한다.

### 안전 최대금액 선계산

사용자가 매매 방식을 선택하면 총 매수금액 없이도 서버가 안전 한도를 계산한다.
이를 위해 `POST /api/v1/analysis-picks/trade-limits`를 추가하고, 기존 안전한도 산식을
`calculate_trade_limits()`로 분리해 preview와 arm 검증이 재사용한다.

한도 요청은 종목, 시장, 매매 방식, 진입가, 목표가, 손절가, 장세를 받는다. 응답은 다음을
포함한다.

- 브로커 현금
- 동일종목 잔여한도
- 포트폴리오 여력
- 손절 위험예산
- 안전 최대금액
- 각 회차를 최소 1주 살 수 있는 최소 주문가능 금액
- 게이트 OFF, 중복 활성 종목, 가격 순서·호가단위 오류 같은 예산 외 차단 사유

프런트는 안전 최대금액의 원 단위 내림값을 `총 매수금액`에 자동 입력하고 input의 `max`로
설정한다. 사용자는 더 적은 양수 금액으로 변경할 수 있다. 안전 최대금액이 최소 주문가능
금액보다 작으면 자동 입력하지 않고 이유를 보여준다.

기존 `안전한도 계산` 버튼은 제거한다. 매매 방식 또는 가격을 바꾸면 이전 preview와 무장
버튼을 무효화하고 한도를 다시 계산한다. 가격 연속 입력 중 과도한 호출을 막기 위해 짧은
debounce를 사용한다.

안전 최대금액을 자동 입력한 직후 기존 `/trade-preview`도 자동 호출해 수량과 예상 주문금액을
보여준다. 사용자가 총 매수금액만 낮추면 한도는 다시 구하지 않고 preview만 갱신한다. 진입가나
손절가를 바꾸면 limits와 preview를 차례로 다시 구한다. `매매 실행·즉시 무장`은 현재 입력과
일치하는 마지막 preview가 통과했을 때만 활성화한다. 최종 `/arm-plan`은 계좌·게이트·중복·
안전한도를 다시 조회한다. 화면에서 계산한 한도나 이전 응답을 신뢰해 서버 재검증을 생략하지
않는다.

## 9. 오류와 동시성

- 분석 저장은 분석 1회당 최대 1행이다.
- 현재가 갱신은 해당 history ID의 가격 열만 업데이트한다.
- 두 번의 가격 갱신이 겹치면 마지막으로 완료된 성공 응답이 최신값이 된다. 분석 원본에는
  영향이 없다.
- 목록 요청 실패와 상세 가격 갱신 실패를 분리한다. 저장된 상세가 있으면 가격 오류 때문에
  상세를 숨기지 않는다.
- 이력 상세에서 전략매매를 열어도 `AnalysisPick`은 생성되지 않는다. 최종 무장 API가
  성공할 때만 기존 방식대로 생성한다.
- 오래된 이력의 계획을 사용할 때도 기존 신선도·게이트·중복·브로커 잔고 검증을 우회하지
  않는다.

## 10. 테스트 계약

### 모델·마이그레이션

- 신규 DB가 `0022_stock_analysis_history` head까지 올라간다.
- PostgreSQL과 SQLite에서 JSON·Text·날짜 열이 생성된다.
- 같은 ticker의 이력 여러 건을 저장할 수 있다.

### API·서비스

- SSE 분석 성공은 이력 1건만 저장하고 완료 이벤트에 `history_id`를 반환한다.
- 같은 ticker 재분석은 새 ID를 만들고 기존 snapshot을 바꾸지 않는다.
- 목록은 최신순이며 대용량 상세 필드를 제외한다.
- 상세 조회는 저장된 snapshot/narrative/trade_plan을 그대로 반환한다.
- 가격 갱신 성공은 `latest_*`만 바꾸고 snapshot/trade_plan/narrative 값은 그대로 유지한다.
- 브로커 가격 실패 시 OHLCV로 폴백하고, 모두 실패하면 503과 기존값 보존을 확인한다.
- 가격 거리 계산은 0 나눗셈과 MANUAL_REQUIRED 계획을 안전하게 처리한다.
- trade-limits는 total_budget 없이 한도를 반환하고 DB를 쓰지 않는다.
- preview와 arm은 같은 한도 계산을 재사용하며 arm은 최신 계좌 상태로 다시 차단할 수 있다.

### 화면

- 종목분석 화면에 이력 목록이 있고 분석 워치 모달에는 중복 목록이 없다.
- 상세 선택은 저장된 분석을 먼저 렌더링한 뒤 가격 갱신 API를 호출한다.
- 재분석은 기존 SSE 경로를 사용하고 완료 후 목록을 갱신한다.
- 저장된 trade_plan이 상세의 전략매매 팝업에 그대로 채워진다.
- 3분할 진입가 세 칸은 공통 필드와 분리된 동일 행이다.
- 매매 방식 선택 후 trade-limits를 호출해 총 매수금액과 max를 자동 설정한다.
- 입력 변경은 과거 preview와 무장 가능 상태를 무효화한다.

### 회귀

- 종목분석·분석 워치·전략매매 집중 테스트
- Alembic fresh DB와 upgrade 테스트
- 전체 Python 테스트
- `node --check static/js/stock-analysis.js`
- 데스크톱·모바일 너비에서 3분할 입력 정렬 수동 확인

## 11. 배포

구현 배포에는 신규 migration `0022_stock_analysis_history`가 포함되므로 운영 DB 백업과
`alembic upgrade head`가 필수다. 배포 후 다음을 확인한다.

- 서비스 active 및 내·외부 health 200
- alembic `0022_stock_analysis_history (head)`
- 분석 1회 후 이력 1건 생성
- 다른 메뉴 왕복 후 목록·상세 복원
- 상세 진입 시 현재가 갱신 시각 변화와 snapshot 불변
- 재분석 후 같은 ticker의 두 번째 행 생성
- 3분할 정렬과 안전 최대금액 자동 입력

push와 운영 배포는 별도의 사용자 요청이 있을 때만 수행한다.
