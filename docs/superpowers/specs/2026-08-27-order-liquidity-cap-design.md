# 자동매수 유동성 하한 설계

## 문제

자동매수가 얇은 종목을 하루 거래대금 대비 과도한 금액으로 산다. 2026-08-20 `195990`
매수가 실제 사례다. 주문 3,331,182원은 그 종목 20거래일 평균 거래대금 37,606,136원의
**8.86%**였다. 같은 기간 나머지 18건은 전부 1.32% 이하였다.

원인은 두 가지이고 서로 다르다.

**원인 1 — 유니버스 유동성 필터가 20일 평균이 아니라 당일 하루치를 본다.**
`maps/ops/scheduler.py`의 `_to_securities`는 그날 수집한 OHLCV 한 행으로
`turnover = close * volume`을 만들어 `turnover_cache[ref_date]`에 넣는다. 이 값을 읽는
`maps/data/security_repo.py`의 `avg_turnover_20d_as_of()`는 docstring이
"ref_date 기준 과거 20일 평균 거래대금(원)"이고, 필터 상수도 `MIN_TURNOVER_KRW`
(KOSPI 5억 / KOSDAQ 3억)다. **이름·문서·의도는 20일 평균인데 실제 값은 하루치다.**

`195990`의 실제 거래대금은 아래와 같다.

| 날짜 | 거래대금 |
|---|---|
| 2026-08-19 | 12,349,038 |
| **2026-08-20** | **336,253,335** (거래량 9,313 → 236,965주) |
| 2026-08-21 | 91,540,368 |

8/20 하루치가 코스닥 하한 3억을 간신히 넘겨 유니버스를 통과했다. 20일 평균은 37,606,136원
으로 하한의 약 1/8이다.

이 결함은 무작위로 새지 않는다. 돌파·던키언 전략은 **거래량 급증일에 신호를 낸다.**
따라서 하루치 판정은 하필 그 전략들이 종목을 고르는 순간에 체계적으로 느슨해진다.

**원인 2 — 주문 경로에 유동성 검사가 아예 없다.**
`maps/ops/order_preview.py`와 `maps/execution/order_manager.py`에는 거래대금 관련 검사가
없다. 유니버스 통과 시점의 판정이 전부이고, 주문 금액이 그 종목의 거래대금 대비 얼마나
큰지는 어디서도 보지 않는다.

## 결정

- 유니버스 필터가 쓰는 유동성 값은 **20거래일 평균 거래대금**이다. 상수와 소비자는
  그대로 두고 채워 넣는 값만 바로잡는다.
- 주문 직전에 **주문금액 ≤ 20일 평균 거래대금 × `MAPS_ORDER_MAX_TURNOVER_PCT`**를
  강제한다. 기본값 `0.02`(2%).
- 한도를 넘으면 주문을 버리지 않고 **수량을 축소**한다.
- 축소 결과가 `MAPS_ORDER_MIN_AMOUNT_KRW`(기본 500,000원) 미만이면 주문하지 않는다.
- 주문 경로와 주문 미리보기가 **같은 순수 함수**를 쓴다.
- **매도에는 적용하지 않는다.**
- 20일 평균 거래대금을 구할 수 없으면 **매수하지 않는다**(fail-closed). 대신 사유를
  반드시 노출한다.
- 전략매매(`analysis_pick`) 경로는 이번 범위가 아니다.
- DB 마이그레이션, 과거 데이터 백필, 새 테이블은 없다.

### 임계값 2%를 고른 근거

최근 60일 체결 매수 19건(집행액 68,508,472원)에 임계값별로 축소를 적용한 결과다.

| 임계값 | 집행액 합계 | 감소 | 축소된 건 |
|---|---|---|---|
| 0.5% | 58,315,787 | −10,192,684 (−14.9%) | 4 |
| 1.0% | 63,698,380 | −4,810,091 (−7.0%) | 3 |
| **2.0%** | **65,929,412** | **−2,579,059 (−3.8%)** | **1** |
| 3.0% | 66,305,474 | −2,202,997 (−3.2%) | 1 |

2%는 확인된 문제 사례 1건만 축소하고 정상 주문 18건을 건드리지 않는다. 3%는 잡는 건수가
같으면서 그 한 건을 더 크게 사게 두므로 2%보다 나은 점이 없다. 1% 이하는 유니버스 하한
근처의 정상 종목까지 상시 축소한다.

## 데이터 흐름

### G1 — 유니버스 (버그 수정)

`_to_securities`는 `historical_ohlcv`에서 **`ref_date`를 포함한 직전 20거래일**의
`avg(close * volume)`을 티커별로 한 번에 집계해 `turnover_cache[ref_date]`에 넣는다.
`avg_turnover_20d_as_of()`, `universe_filter`의 `low_turnover` 판정,
`scheduler`의 유동성 정렬은 코드 변경 없이 올바른 값을 받는다.

`ref_date` 당일 봉을 포함하는 것은 기존 동작과의 연속성 때문이다. 지금도 당일 수집분을
쓰고 있고, 후보 생성은 수집(16:40) 이후 16:50에 돌아 당일 봉이 이미 확정돼 있다.
`ref_date` **이후** 데이터는 쓰지 않으므로 as-of-date 생성기 제약(CLAUDE.md 제약 1번)을
깨지 않는다.

집계된 거래일 행이 20개 미만이면 **있는 만큼의 평균**이 아니라 **미달로 취급**한다.
신규 상장 때문이 아니다 — 유니버스는 이미 `MIN_LISTING_DAYS = 100`을 요구하므로 여기까지
온 종목은 상장 100일을 넘겼다. 행이 모자라는 경우는 **거래정지 구간이나 수집 누락**이며,
그런 종목의 부분 평균을 정상 유동성으로 인정하지 않겠다는 뜻이다.

### G2 — 주문 시점 (신규)

`maps/ops/liquidity_cap.py`에 순수 함수를 둔다.

```python
@dataclass(frozen=True)
class LiquidityCapResult:
    qty: int                      # 최종 수량. 0 이면 주문하지 않는다
    original_qty: int
    reason: str | None            # 아래 사유 코드
    turnover_20d: float | None
    limit_amount: float           # turnover_20d * pct

def apply_liquidity_cap(
    *, qty: int, price: float, turnover_20d: float | None, settings: MapsSettings
) -> LiquidityCapResult: ...
```

사유 코드는 셋이다.

| 코드 | 뜻 |
|---|---|
| `LIQUIDITY_CAPPED` | 한도에 맞춰 수량을 줄였다. 주문은 나간다 |
| `BELOW_MIN_ORDER_AMOUNT` | 줄인 결과가 최소 주문금액 미만이라 주문하지 않는다 |
| `TURNOVER_UNAVAILABLE` | 20일 평균 거래대금을 구할 수 없어 주문하지 않는다 |

`TURNOVER_UNAVAILABLE`일 때 `limit_amount`는 `0.0`이다 — 한도를 계산할 수 없다는 뜻이지
한도가 0이라는 뜻이 아니므로, 표시할 때 "한도 0원"으로 쓰지 않는다.

`MAPS_ORDER_MAX_TURNOVER_PCT`가 `0`이면 이 게이트는 비활성이고 `qty`를 그대로 돌려준다.

주문 경로(`scheduler`의 매수 수량 확정 지점)와 `order_preview`가 이 함수를 호출한다.
경로마다 따로 구현하지 않는다 — 손절가가 사이징과 화면에서 갈려 포지션이 두 배로 잡혔던
2026-07-29 사고와 같은 구조이기 때문이다(CLAUDE.md 제약 7번).

## 설정

| 키 | 기본값 | 뜻 |
|---|---|---|
| `MAPS_ORDER_MAX_TURNOVER_PCT` | `0.02` | 주문금액 / 20일 평균 거래대금 상한. `0` 이면 비활성 |
| `MAPS_ORDER_MIN_AMOUNT_KRW` | `500000` | 축소 후 이 금액 미만이면 주문하지 않는다 |

## 노출

축소·차단은 조용히 일어나면 안 된다. 사용자가 "왜 안 샀지" 또는 "왜 이만큼만 샀지"를
화면에서 답할 수 있어야 한다.

- 주문 미리보기: 축소된 행에 원래 수량, 축소 수량, 한도 금액, 사유를 표시한다.
- 일일 다이제스트: 축소·차단 건수와 종목별 사유를 싣는다.
- 매매일지 규칙: 축소된 주문을 원래 계획대로 산 것처럼 서술하지 않는다.

## 위험

**fail-closed가 전량 차단으로 번질 수 있다.** 거래대금 데이터가 비면 매수가 전부 멎는다.
2026-08-14에 수급 NULL 하나 때문에 신규 매수가 사흘간 전량 막혔고, 그 사흘을 아무도
알아채지 못했다. 같은 실패 양상이다. 그래서 `TURNOVER_UNAVAILABLE`은 반드시 화면과
다이제스트에 사유로 드러나야 하며, 이 노출은 선택 사항이 아니라 게이트의 일부다.

**G1 수정이 후보 수를 줄일 것으로 봤으나, 실측 결과 반대였다.** 2026-08-27 운영 데이터로
최근 5거래일을 재보니 탈락률이 오히려 낮아진다.

| 기준일 | 기존(당일 1일치) | 신규(20일 평균) |
|---|---|---|
| 2026-08-21 | 52.7% | 45.1% |
| 2026-08-24 | 55.3% | 45.2% |
| 2026-08-25 | 54.4% | 45.4% |
| 2026-08-26 | 55.5% | 45.3% |
| 2026-08-27 | 55.0% | 46.1% |

당일 하루치 기준은 **양방향으로 틀렸다.** 코스닥 2026-08-27 기준으로 분해하면 급등일 하루로
새어 들어오던 40종목이 차단되는 동시에, 거래가 뜸한 날 하루 때문에 억울하게 탈락하던
222종목이 구제된다(20봉 미만 이력 부족은 6종목). 즉 이 수정은 게이트를 조이는 것이 아니라
**정확하게** 만든다.

`REJECTION_ALERT_THRESHOLD`(0.40)는 신규 기준에서도 넘지만 기존 기준은 이미 55%로 넘고
있었다 — 거부율 알림은 새로 생기는 소음이 아니라 오히려 줄어든다.

## 테스트

TDD로 각 단계마다 실패 테스트를 먼저 쓴다.

- G1: 하루만 급등한 종목이 20일 평균 기준으로 `low_turnover` 판정을 받는다
  (`195990` 실제 수치를 픽스처로 쓴다). 이력이 20거래일 미만이면 미달 처리된다.
- G2: 한도 초과 시 수량이 한도 이하로 줄고, 한도 이내면 그대로 통과한다.
  축소 결과가 최소 금액 미만이면 `qty=0`과 `BELOW_MIN_ORDER_AMOUNT`.
  `turnover_20d`가 `None`이면 `qty=0`과 `TURNOVER_UNAVAILABLE`.
  `MAPS_ORDER_MAX_TURNOVER_PCT=0`이면 원래 수량 그대로.
- 공유: 주문 미리보기와 주문 경로가 같은 입력에서 같은 수량을 낸다.
- 매도: 매도 주문은 이 게이트를 통과하지 않는다.
