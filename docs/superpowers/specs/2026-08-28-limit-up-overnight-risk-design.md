# 상한가 V1 오버나이트 위험 통제 설계

## 문제

`feat/limit-up-v1` 의 상한가 엔진은 종가에 상한가로 잠긴 종목을 익일 시가까지 보유한다
(`LimitUpState.OVERNIGHT` → `service.sell_next_open()`). 그런데 **오버나이트 구간에는 손실
통제 수단이 하나도 없다.**

- 하드손절 −5%(`live_rules` 의 `limit_up_v1`, 진입가 기준 `effective_stop_price`)는 장중에만 작동한다.
- 익일 청산은 시가 단일가 시장가 매도라 가격을 지정하지 않는다.
- 즉 정규장이 닫힌 뒤 악재가 나오면, 다음 날 하한가로 시작하더라도 그대로 맞는다.

현재 파라미터로 이 노출을 계산하면 확정된 위험 한도를 **수학적으로 위반한다.**

| 항목 | 값 | 근거 |
|---|---|---|
| 종목당 예산 | 2,000,000원 | `service.py:471` `budget = 2_000_000` (하드코딩) |
| 동시보유 | 2종목 | `domain.py` `can_enter(active_sessions < 2)` |
| 오버나이트 최대 노출 | 4,000,000원 | 위 둘의 곱 |
| 익일 하한가 손실 | **−1,200,000원** | 4,000,000 × 0.30 |
| 비상 절대상한 | −1,000,000원 | 확정 요구사항 |

**200,000원 초과다.** 이 상태로 `AUTOMATIC` 을 켜면 가드가 뚫린다.

### 부수 발견 — 일일 중단선이 배선되어 있지 않았다 (✅ 해소)

`DailyGuard.update_daily_pnl()` 의 호출부가 코드 어디에도 없었다. 단위 테스트
(`tests/test_limit_up_domain.py`) 한 곳에서만 불러서, 확정 요구인 **−300,000원 일일
자동중단선이 작동하지 않았다.** 살아 있던 나머지 가드 3개(시도 5회·패턴실패 2회·코스닥
−1.5%)는 전부 횟수·지수 기준이라 손실 금액과 무관했고, 죽어 있던 하나가 **유일한 금액
기반 가드**였다.

**1-1 실현손익 원장과 함께 배선을 마쳤다.** 아래 1-1 절이 구현된 상태를 기술한다.
1-2 오버나이트 위험 예산은 이 원장을 그대로 입력으로 쓰면 된다 — 선행 작업은 끝났다.

## 확정된 방침

**오버나이트를 유지한다.** 상한가에 잠긴 채 마감한 종목을 익일 시가까지 가져가는 것이 이
전략의 핵심 수익원이다. 대신 갭하락 위험을 두 겹으로 막는다.

1. **포지션 사이징 — 1차 방어선.** 익일 하한가(−30%)를 맞아도 손실이 절대상한을 넘지
   않도록 오버나이트 노출 금액 자체를 제한한다. 수학적 보증이다.
2. **시간외 붕괴 감시 — 2차 방어선.** 16:00~18:00 시간외 단일가에서 상한가가 무너지는
   징후를 잡아 그날 저녁에 탈출한다. 확률을 낮추는 보조 수단이지 보증이 아니다.

이 순서가 중요하다. 2번이 실패해도 1번이 −1,000,000원을 보증한다.

## 1절. 실현손익 원장과 오버나이트 위험 예산

### 1-1. 실현손익 원장 (선행 작업) — ✅ 구현 완료

청산 체결이 확인되면 실현손익을 계산해 `limit_up_session.realized_pnl` 에 남긴다.
`DailyGuard` 는 값을 메모리에 누적하지 않고 **당일 세션 합으로 재구성**한다
(`repository.realized_pnl_total(ref_date)`). 프로세스가 재시작되어도 복원된다.

손익은 체결금액 기준에 매도세·수수료를 반영한 순액으로 잡는다(`domain.realized_pnl()`).
비용을 빼고 계산하면 한도가 실제보다 느슨해진다.

구현하며 확정한 것:

- **부분청산은 체결 수량만 대응시킨다.** 미청산분은 미실현이므로 전액 원가를 물리지 않는다.
- **미체결 청산은 `0` 이 아니라 `NULL` 로 둔다.** 제출 직후 브로커가 아직 체결을 돌려주지
  않은 상태를 `0` 으로 기록하면 손실이 한도에서 조용히 사라진다. 값은 다음 `reconcile()`
  이 채운다. 정산은 `reconcile()` 이 이미 부르는 `get_daily_order_results()` 스냅샷을
  재사용하므로 **브로커 호출이 늘지 않는다** (청산 주문 id는 `limit_up_session.exit_order_id`).
- **갱신 시점은 진입 심사 직전 한 곳이다** (`service._refresh_daily_pnl()`). 손익은 청산으로만
  변하고, 심사 순간에 DB에서 다시 읽으므로 재시작·복구 경로가 따로 필요 없다.
- **`RECOMMEND_ONLY` 모드는 체결이 없어 합이 0 이다.** 실제 계좌 손실이 없으므로 중단선의
  대상이 아니다. 추천 신호의 가상 손익으로 중단선을 걸려면 가상 청산 엔진이 선행돼야 하고,
  그것은 이 작업 범위 밖이다.
- `−300,000` 은 `domain.DAILY_LOSS_LIMIT_KRW` 상수다. 1-3 방침대로 설정으로 열지 않는다.

이 원장은 두 곳이 함께 쓴다.

- 기존 −300,000원 일일 자동중단선 (`DailyGuard.update_daily_pnl`) — 지금 죽어 있는 배선
- 아래 1-2 오버나이트 위험 예산

### 1-2. 위험 예산 산식 — ✅ 구현 완료 (`domain.overnight_budget`)

```
LIMIT_DOWN_RATIO = 0.30          # 익일 하한가
ABSOLUTE_CAP_KRW = 1_000_000     # 비상 절대상한

overnight_budget = (ABSOLUTE_CAP_KRW - max(0, -realized_pnl_today)) / LIMIT_DOWN_RATIO
```

| 당일 실현손익 | 허용 노출액 | 2종목 균등 시 | 최악 손실 | 합산 |
|---|---|---|---|---|
| 0원 | 3,333,333원 | 각 1,666,666원 | −1,000,000원 | −1,000,000원 |
| −300,000원 | 2,333,333원 | 각 1,166,666원 | −700,000원 | −1,000,000원 |
| +500,000원 | 3,333,333원 | 각 1,666,666원 | −1,000,000원 | −500,000원 |

`max(0, ...)` 이 핵심이다. **실현이익은 한도를 늘리지 않는다.** 이익으로 한도를 키우면
절대상한이 그날의 운에 따라 흔들린다.

노출액은 **당일 종가(=상한가) 기준**으로 센다. 익일 하한가가 종가의 70%이므로 최대손실이
정확히 `노출액 × 0.30` 이 된다.

### 1-3. 하드 플로어 — ✅ 적용

`ABSOLUTE_CAP_KRW` 와 `LIMIT_DOWN_RATIO` 는 설정으로 노출하지 않고 상수로 둔다. 유동성
하한 500억이 `LimitUpConfig.__post_init__` 에서 낮춤을 예외로 막는 것과 같은 방식이다.
설정으로 열어 두면 위험 한도가 조용히 느슨해진다.

## 2절. 15:18 심사 개편 — ✅ 구현 완료

현재 `service.review_eod()` 는 hold / 전량매도 두 갈래다. 여기에 트림 단계를 넣는다.

```
15:18  ① eod_hold_allowed() 심사 — 탈락하면 종전대로 전량청산 (변경 없음)
       ② 통과 세션들에 위험 예산을 균등 배분
       ③ 허용수량 = floor(배분액 / 상한가)
          초과분 = 보유수량 − 허용수량
       ④ 초과분 > 0 → 상한가 지정가 매도 제출, 상태 EOD_TRIM
15:25  ⑤ 재확인 — 전량 체결됐으면 OVERNIGHT 전이
15:28  ⑥ 미체결 잔존 → 해당 종목 전량 시장가 청산
          end_reason = "overnight_cap_unfilled"
```

### 결정 근거

**예산 배분은 균등이다.** 잔량비율 우선순위 같은 규칙은 V1에 넣지 않는다.

**진입 시점이 아니라 15:18에 조인다.** 진입 시점부터 캡을 걸면 당일 청산으로 끝날 대부분의
거래까지 17% 작아져 전략 수익력이 같이 깎인다. 오버나이트로 넘길 세션에만 캡을 적용한다.

**미체결이면 오버나이트를 포기한다.** 캡을 못 맞추면 넘기지 않는다. 데이터·체결 사고가 나도
절대상한을 뚫을 경로가 없다. 유동성 하한·점수 준비도 게이트가 fail-closed 인 것과 같은
방향이다. 다만 이 실패는 드물 것이다 — 오버나이트 허용 조건 자체가 *매수잔량 ≥ 상장주식수
1% + 30억* 이라 상한가 호가에 던지면 두터운 매수벽에 체결된다.

### 구현하며 확정한 것

- 세 단계는 `service.apply_overnight_cap()` / `confirm_overnight_cap()` /
  `force_overnight_cap()` 이고, 시각 훅은 `runtime.eod_stage()` 가 정한다. 창을 벗어나면
  그 회차가 영영 없는 조용한 실패라 시각 경계를 테스트로 고정했다.
- **허용수량은 회차마다 재계산한다.** 15:18에 얼려두지 않는다 — 사이에 한 세션이 청산되면
  남은 세션이 예산을 다시 나눠 갖는 것이 맞다.
- **트림 매도는 상한가 지정가다.** 오버나이트 심사 자체가 *매수잔량 ≥ 상장주식수 1%* 를
  요구하므로 그 매수벽에 지정가로 던지면 체결된다. 시장가로 내면 호가를 타고 내려가
  애써 잠근 종가를 스스로 깎는다.
- **15:28 강제청산 전에 미체결 트림 주문을 반드시 취소한다**(`worker.cancel_open_exits`).
  취소 없이 전량매도를 얹으면 보유수량보다 많이 판다.

> 🔴 **구현 중 발견한 기존 결함 2건** (둘 다 수정함)
>
> ① **멱등 키 충돌.** `repository.transition(action=...)` 이 이미 그 `state_version` 에
> 이벤트를 남기므로, worker 가 *같은 action 이름* 으로 `event_exists` 를 검사하면 항상 True 가
> 되어 **주문이 조용히 건너뛰어진다.** worker 의 제출 의도는 별도 action 이름
> (`overnight_trim_sell`)을 써야 한다.
>
> ② **`OrderManager.cancel()` 이 `order_log` 상태를 안 내렸다.** 브로커에서 취소된 주문이
> 로그에는 `pending` 으로 남아, 같은 종목을 다시 팔려는 정상 주문이
> `_raise_if_duplicate_active_order` 에 막혔다. 취소된 주문이 살아 있는 것으로 기록되는 것
> 자체가 감사 오류이므로 취소 지점에서 고쳤다 — `limit_up` 전용 우회를 만들지 않았다.
> **이 수정은 `cancel()` 의 모든 호출자에 적용된다.**

### 상태

`EOD_TRIM` 을 추가한다. 15:25·15:28 재확인을 하려면 "초과분 매도 대기"를 상태기계가 들고
있어야 한다. 시각 훅은 `runtime.py:312` 의 15:18~15:20 처리부를 확장한다(장중이므로 runtime
소관, 시간외 감시만 스케줄러로 간다).

## 3절. 시간외 붕괴 감시 (16:00~18:00) — ✅ 구현 완료 (🟡 실환경 미검증 2건)

정규장에 상한가로 마감했더라도 장 종료 후 악재 공시나 해외지수 급락으로 시간외 단일가에서
상한가가 무너지는 일이 있다. 시간외에서 무너지면 익일 갭하락은 사실상 확정이다.

### 3-1. 폴링 스케줄

잡 하나에 트리거 두 개를 건다. 감시 회차와 마감 정리 회차는 하는 일이 다르다.

```python
# 감시: 16:00:05 ~ 17:50:05 (12회)
CronTrigger(day_of_week="mon-fri", hour="16-17",
            minute="0,10,20,30,40,50", second=5)

# 마감 정리: 18:00:05 (1회)
CronTrigger(day_of_week="mon-fri", hour=18, minute=0, second=5)
```

- KRX 시간외 단일가는 16:00~18:00 사이 10분 단위로 접수·체결한다. 체결은 **16:10 최초 →
  18:00 최종까지 12회** 일어난다.
- 감시 폴링은 그보다 한 턴 앞선 16:00~17:50에 12회 돈다. 16:00 회차는 첫 체결(16:10) 전이라
  no-op이며, 3-3의 거래량 가드가 이를 처리한다.
- **17:50 회차가 마지막 실효 회차다.** 여기서 낸 주문이 18:00 최종 체결에 걸린다. 그 이후에
  감지해 봐야 실행할 회차가 남지 않는다.
- 18:00:05 회차는 판정하지 않는다. 최종 체결 결과를 기록하고 세션을 확정할 뿐이다.
- `second=5` 는 KRX 매칭 → KIS API 반영 지연(통상 1~3초) 버퍼다. 정각에 폴링하면 방금
  체결된 값이 아니라 10분 전 값으로 판정할 위험이 있다.

매 회차가 하는 일은 셋뿐이다 — `state='overnight'` 세션 조회 → 시간외 시세 폴링 → 판정·매도.
대상이 없으면 DB 조회 한 번으로 끝난다. 16:40 수집·16:50 후보생성과 같은 스케줄러를 쓰므로
**회차당 실행을 초 단위로 묶는 것이 설계 제약이다.**

### 3-2. 판정과 탈출

```
트리거:  시간외 체결가 ≤ 당일 종가 × 0.98        (-2%)
동작:    보유 전량 매도
가격:    round_down_krx_price(당일 종가 × 0.90)   ← 시간외 하한가, 호가단위 내림
재제출:  없음. 1회 제출 후 체결만 감시
18:00 경과: 오버나이트 유지 → 익일 시가 청산 경로 + 경보
```

**하한가로 던지는 이유.** 시간외 거래는 10분마다 주문을 모아 하나의 가격으로 체결하는
단일가 매매다. 지정가는 *체결 우선순위*를 정하지 *체결 가격*을 정하지 않는다. 하한가로
제출해도 실제 체결은 그 회차 단일가(예: −3%)로 일괄 이뤄진다. 반대로 직전 체결가(−2%)로
내면, 다음 회차 단일가가 −4%로 결정될 때 가격 우선 원칙에 밀려 한 주도 체결되지 않는다.
10분마다 뒷북을 치다 18:00까지 못 파는 것이 최악의 시나리오다.

**호가단위 내림이 필수다.** `종가 × 0.9` 를 그대로 보내면 유효하지 않은 가격으로 주문이
거부된다. 예: 종가 39,450원 → 35,505원 → 3만원대 호가단위 50원 → **35,500원**. 매도이므로
반드시 내림이다. `maps/market/trading_rules.round_down_krx_price()` 를 재사용한다(새로 만들지
않는다).

**재제출 루프가 없는 이유.** KRX 시간외 단일가에서 미체결 주문은 명시적으로 취소하지 않는 한
18:00 최종 회차까지 이월 생존한다. 이미 최우선 가격이므로 갱신할 이유가 없다. 재제출 경로가
없으므로 "미체결을 오류로 오인해 중복 주문" 이라는 실패 양상도 구조적으로 생기지 않는다.

> 🟡 **이월이 미검증이므로 조용한 실패만 막아 뒀다.** 구현 중 "주문이 사라졌고 보유가 남으면
> 재제출" 을 시도했으나, `OrderManager._raise_if_duplicate_active_order` 에 막힌다.
> 우회하려면 낡은 `order_log` 행을 먼저 정리하는 로직이 필요한데, **회차 이월 여부를 모르는
> 상태에서 그걸 만드는 것은 복잡도만 사고 안전은 못 산다.** 그래서 재제출 대신 ERROR 로그를
> 남긴다(`after_hours.py`). 실검증에서 이월이 안 되는 것으로 판명되면 그때 제대로 만든다.

### 3-3. 정상과 이상의 구분

| 상황 | 판정 | 동작 |
|---|---|---|
| 시간외 **누적 거래량 = 0** | 정상 | 가격 비교 자체를 스킵 |
| 체결가가 `0` / `null` | 이상 데이터 | 스킵 + 경보 |
| 폴링 실패(API 오류) | 이상 | 경보 후 다음 회차 재시도. **팔지 않는다** |
| 체결가 ≤ 종가 × 0.98 | 붕괴 | 전량 탈출 + 알림 |

**거래량 가드가 반드시 가격 비교보다 먼저다.** 상한가 종목은 시간외에 매도 물량이 없어
거래가 아예 없을 수 있다. 이때 API가 `0` 을 돌려주는데 그대로 산술 비교에 넣으면 시스템이
−100% 폭락으로 오인해 첫 회차부터 전량 매도한다. 이것은 fail-open보다 나쁜 fail-wrong 이다.

> 🔵 **구현 시 설계 변경 — 판정을 "누적거래량 0" 이 아니라 "직전 회차 대비 증가" 로 바꿨다.**
> 시간외 시간대에 KIS `acml_vol` 이 시간외 거래량인지 당일 전체 누적인지 **실측 없이 확정할
> 수 없다.** 당일 전체라면 정규장 거래량 때문에 `0` 이 절대 아니게 되어 원안 가드가 통째로
> 무력화된다. 직전 회차와 비교하면 **어느 쪽이든 "이 회차에 새 체결이 있었나"** 를 옳게
> 판정한다. 직전값은 `limit_up_session.after_hours_volume` 에 남긴다.
>
> 같은 이유로 별도 시간외 TR ID 를 추측하지 않고 **이미 검증된 `inquire-price`
> (FHKST01010100)** 를 쓴다. 문서에 없는 TR ID 를 넣는 것이야말로 이 설계가 경고한
> "상수 하나가 틀려 조용히 작동하지 않는" 실패다.

**폴링 실패에 fail-closed 를 적용하지 않는다.** 못 파는 것이 아니라 *판단을 못 하는* 것이고,
이때 강제 매도하면 멀쩡한 포지션을 API 장애로 던지게 된다.

### 3-4. 상태

`AFTER_HOURS_EXIT` 을 추가한다. 역할은 "재제출 대기"가 아니라 **"제출 완료·체결 감시"**다.
중복 제출 방지는 새 래치를 만들지 않고 기존 멱등 장치
(`repository.event_exists(action=..., state_version=...)`)를 그대로 쓴다.

### 3-5. 구조적 한계 (설계된 한계이며 결함이 아니다)

1. **금요일 오버나이트는 월요일 시가까지 3일**인데 시간외 감시는 금요일 당일 2시간뿐이다.
   주말 악재는 방어 수단이 없다.
2. **앱이 죽어 있으면 감시도 없다.** 16:00~18:00 재시작·배포가 겹치면 구멍이 생긴다.
   현재 `stock_report` 잡이 18:00이라 마지막 정리 회차와 겹친다.
3. 시간외 감시는 갭하락 확률을 줄이는 장치이지 제거하는 장치가 아니다. −1,000,000원 보증은
   전적으로 1절 사이징이 담당한다.

| 구분 | 항목 |
|---|---|
| 새 컬럼 | `limit_up_session.realized_pnl` (Float, nullable) — ✅ 적용 |
| 새 컬럼 | `limit_up_session.exit_order_id` (String(128), nullable) — ✅ 적용. 정산이 청산 체결을 되찾는 열쇠 |

| KIS 어댑터 | `place_after_hours_sell()`, `get_after_hours_quote()` (체결가 + **누적거래량** 동반 반환) |
| 스케줄러 | `limit_up_after_hours` 잡 1개 |

`get_after_hours_quote()` 가 체결가와 누적거래량을 **함께** 반환해야 한다. 따로 조회하면
3-3의 거래량 가드가 서로 다른 시점의 값을 비교하게 된다.

**마이그레이션은 `0029_limit_up_v1` 에 흡수한다.** 0029는 아직 커밋되지 않았고 운영 head 는
`0028_holding_regime_audit` 이라 어디에도 적용된 적이 없다. 별도 0030을 쌓으면 존재한 적 없는
스키마를 고치는 마이그레이션이 남는다.

## 5절. 테스트

### 단위

- 위험예산 산식 경계값 — 실현손익 `0` / `−300,000` / **이익 난 날**(한도가 늘지 않는지)
- 예산 균등 배분, 허용수량 `floor` 처리
- 호가단위 내림 — 39,450원 사례 포함
- 유령 데이터 가드 — `volume=0`, `price=0`, `price=None` 각각
- 트리거 경계 — 정확히 `종가 × 0.98` 일 때 (경계 포함 여부를 테스트가 고정한다)
- 신규 상태 전이 — `EOD_TRIM`, `AFTER_HOURS_EXIT`

### 통합

- 15:18 → 15:25 → 15:28 세 갈래: 전량체결 / 부분체결 / 미체결
- 시간외 탈출 세 갈래: 체결 / 미체결로 18:00 경과 / 폴링 실패
- 폴링 실패가 **매도를 유발하지 않는** 것을 명시적으로 고정

### 소스 가드

매도 가격 계산이 한 곳에만 존재함을 고정하는 테스트. 유동성 하한의
`test_preview_and_order_paths_share_one_implementation` 과 같은 방식이다. 가격 계산이 경로마다
갈리면 화면과 실주문이 어긋난다(CLAUDE.md 제약 7번과 같은 실패 유형).

### 실환경 검증 — 🟡 **미완. 구현은 끝났으나 이 둘이 확정되기 전에는 `automatic` 모드로
시간외 탈출을 신뢰하지 말 것.**

아래 둘은 **문서 대조만으로 끝내지 않는다.** 상수 하나가 틀리면 탈출이 조용히 작동하지 않은
채 "−2% 감지" 로그만 남는다. 검증 비용이 낮으므로 반드시 실행한다.

1. **`ORD_DVSN=21` 확정** — KIS 국내주식 주문 `ORD_DVSN` 표 대조 + **모의계좌로 16:00~18:00
   사이 1주 매도 주문 실제 제출**. 접수되면 확정.
2. **미체결 이월 확인** — 위 주문을 그대로 두고 다음 회차에 살아 있는지 확인. 회차마다
   소멸한다면 3-2의 "재제출 없음" 이 무너지고 래치 설계가 되살아난다.
