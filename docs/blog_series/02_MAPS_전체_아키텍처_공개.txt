[MAPS 이야기 #2] MAPS 전체 아키텍처 공개

직접 만들어보려는 분들이 가장 궁금해할 부분입니다.
MAPS가 어떤 부품으로 조립돼 있는지 그대로 적습니다.


────────────────────
1. 기술 스택
────────────────────

▸ 언어 : 파이썬
▸ 웹 : FastAPI, Jinja2 대시보드
▸ DB : PostgreSQL (개발 환경은 SQLite), 스키마 변경은 Alembic
▸ 스케줄 : APScheduler
▸ 데이터 : pykrx, yfinance, 네이버 금융
▸ 증권사 : 한국투자증권 REST API
▸ 앱 : Capacitor 기반 안드로이드
▸ 서버 : AWS Lightsail 1대, nginx, systemd

저는 자바를 오래 다뤄온 사람입니다.
그런데 이 시스템은 파이썬으로 만들었습니다.
가격 데이터를 다루는 라이브러리 차이가 너무 큽니다.
같은 백테스트를 자바로 쓰면 분량이 서너 배로 늘어납니다.

서버는 한 대, 구조는 단일 애플리케이션입니다.
혼자 만드는 시스템에 마이크로서비스를 얹으면 장애 지점만 늘어납니다.


────────────────────
2. 층 구조
────────────────────

기능을 층으로 나누고, 각 층은 아래층만 참조하게 했습니다.

  data          가격·종목 정보 수집과 저장
  data_quality  거래정지·관리종목을 걸러낸 대상 종목 생성
  indicator     추세 강도 점수 계산
  strategy      매매 규칙 8종
  backtest      과거 재현, 거래비용 반영
  validation    워크포워드·파라미터 안정성·몬테카를로
  promotion     검증 결과로 승격 여부 판정
  market        시장 국면 분류, KRX 거래일·호가 규칙
  risk          손실 한도와 킬 스위치
  execution     주문 생성과 증권사 어댑터
  ops           스케줄 실행, 알림, 일일 집계
  api           화면별 라우터

핵심은 execution 층입니다.
증권사 접속을 추상 인터페이스로 두고 그 뒤에 모의 브로커와
실제 증권사 어댑터를 갈아 끼웁니다.
전략 코드는 지금 어느 계좌에 붙어 있는지 알지 못합니다.


────────────────────
3. 값은 한 곳에만 둡니다
────────────────────

손절가를 예로 들면, 계산 함수가 시스템 전체에 하나뿐입니다.
청산 판정, 수량 계산, 화면 표시가 모두 그 함수를 거칩니다.

같은 숫자를 두 곳에서 계산하면 언젠가 한쪽만 고쳐집니다.
실제로 그 일이 있었습니다. 수량 계산만 옛 방식을 쓰는 바람에
어떤 종목은 의도한 위험의 두 배로 포지션이 잡혔습니다.
지금은 함수 하나로 합쳤고, 그 규칙을 문서 맨 앞에 못 박아 뒀습니다.

승격 이력, 종목 선정 품질 로그, 주문 로그, 킬 스위치 로그.
이 네 개 테이블은 프로젝트 첫날부터 있었습니다.
"왜 이 종목을 샀지"라는 질문은 반드시 나오고,
그때 답하지 못하면 시스템을 신뢰할 근거가 사라집니다.
