# limit_up/

상한가 당일매매 V1 엔진. 일봉 `BaseStrategy` 와 **별도 패키지**다 — 장중 실시간 신호와
주문 경로가 기존 일봉·익일주문 구조와 근본적으로 다르기 때문이다.

> ⚠️ **배선은 됐지만 기본은 꺼져 있다.** `MAPS_LIMIT_UP_ENABLED=false`(기본)면
> `main.py` 수명주기가 엔진을 띄우지 않는다 — 스케줄러와 같은 방침이다.
> 켜져 있어도 `MAPS_BROKER_MODE=kis` 가 아니면 **기동을 거부**한다(실시간 시세가
> 없는 브로커로 띄우면 트리거가 영영 안 걸리는 좀비 엔진이 된다).
> 기동 실패는 API 서버를 죽이지 않는다 — 엔진을 끄는 관리자 엔드포인트가 살아 있어야 한다.

## Directory structure

```
limit_up/
├── __init__.py       # 빈 패키지 마커
├── after_hours.py    # 16:00~18:00 시간외 붕괴 감시·탈출 (스케줄러 소관)
├── bootstrap.py      # 엔진 조립·기동 게이트·런타임 핸들
├── domain.py         # 순수 상태기계·가격 규칙·일일 가드·위험 예산
├── feed.py           # KIS 실시간 메시지 정규화, 테이프 링버퍼
├── repository.py     # 세션·레그·이벤트 영속과 멱등 키
├── runtime.py        # asyncio 수명주기, 웹소켓, 15:18~15:28 시각 훅
├── service.py        # 이벤트 → 상태 → 브로커 명령 조정
└── worker.py         # 브로커 명령 실행 (순서는 runtime 펌프가 잡는다)
```

## 위험 통제 — 세 겹

이 전략의 손실 한도는 **확정 요구**이지 튜닝 대상이 아니다. 아래 값은 전부
`domain.py` 상수이고 **설정으로 노출하지 않는다**. 설정으로 열면 위험 한도가 조용히
느슨해진다 — 유동성 하한 500억을 `LimitUpConfig.__post_init__` 이 막는 것과 같은 방침이다.

| 상수 | 값 | 의미 |
|---|---|---|
| `DAILY_LOSS_LIMIT_KRW` | `-300_000` | 평상시 일일 자동중단선 (원금 2,000만의 −1.5%) |
| `ABSOLUTE_CAP_KRW` | `1_000_000` | 비상 절대상한 (주문 오류·갭·체결 지연 포함) |
| `LIMIT_DOWN_RATIO` | `0.30` | 익일 하한가 |
| `AFTER_HOURS_FLOOR_RATIO` | `0.90` | 시간외 하한 |

### 1. 일일 중단선 — `DailyGuard`

가드 4개 중 **금액 기반은 `update_daily_pnl` 하나뿐**이다. 나머지 셋(시도 5회·패턴실패
2회·코스닥 −1.5%)은 횟수·지수 기준이라 손실 금액과 무관하다.

`DailyGuard` 는 손익을 메모리에 누적하지 **않는다.** 진입 심사 직전에
`repository.realized_pnl_total(ref_date)` 로 **당일 세션 합에서 재구성**한다 —
프로세스가 재시작돼도 계좌가 실제로 입은 손실에 그대로 걸린다.

> `ref_date` 는 KST 거래일이다. `created_at`(UTC naive)으로 계산하면 09:00 KST 이전에
> 하루씩 어긋난다.

### 2. 오버나이트 사이징 — 수학적 보증

```
overnight_budget = (1,000,000 − max(0, 당일 실현손실)) / 0.30
```

**실현이익은 한도를 늘리지 않는다.** 이익으로 한도를 키우면 절대상한이 그날의 운에 따라
흔들린다. 노출은 당일 종가(=상한가) 기준으로 세므로 최대손실이 정확히 `노출 × 0.30` 이다.

진입 시점이 아니라 **15:18 에 조인다.** 진입부터 캡을 걸면 당일 청산으로 끝날 대부분의
거래까지 작아져 전략 수익력이 함께 깎인다.

| 시각 | 함수 | 하는 일 |
|---|---|---|
| 15:18 | `service.apply_overnight_cap()` | 초과분 → 상한가 지정가 매도, `EOD_TRIM` |
| 15:25 | `service.confirm_overnight_cap()` | 전량 체결됐으면 `OVERNIGHT` 복귀 |
| 15:28 | `service.force_overnight_cap()` | 미체결이면 트림 취소 후 **전량청산** |

15:28 이 fail-closed 인 것이 보증의 핵심이다 — 캡을 못 맞추면 오버나이트를 포기한다.
허용수량은 회차마다 재계산한다(그 사이 한 세션이 청산되면 남은 세션이 다시 나눠 갖는다).

### 3. 시간외 붕괴 감시 — 보조 수단

`after_hours.py`, 16:00~17:50 매 10분 + 18:00 마감 정리. **확률을 낮추는 장치이지 보증이
아니다** — −1,000,000원 보증은 전적으로 2번 사이징이 담당한다.

- **거래량 가드가 가격 비교보다 먼저다.** 상한가 종목은 시간외에 매도 물량이 없을 수 있고,
  그때 API 가 `0` 을 주면 −100% 폭락으로 오인해 첫 회차에 전량 매도한다. fail-open 보다
  나쁜 **fail-wrong** 이다. 판정은 *직전 회차 대비 누적거래량 증가* 로 하므로, 브로커
  카운터가 시간외 전용이든 당일 전체든 옳게 동작한다.
- **폴링 실패는 팔지 않는다.** 못 파는 게 아니라 *판단을 못 하는* 것이다.
- **하한가 지정가로 던진다.** 단일가 매매라 지정가는 체결 *우선순위*만 정하고 체결가는 그
  회차 단일가로 난다. 직전 체결가로 내면 가격이 밀리는 회차마다 뒷북을 치다 못 판다.
- **재제출하지 않는다.** 미체결 주문은 18:00 까지 이월 생존하는 것으로 본다.

> 🟡 **실환경 미검증 2건.** ① `ORD_DVSN=21`(`kis_adapter._AFTER_HOURS_ORD_DVSN`)
> ② 미체결 주문의 회차 이월. 둘 다 모의계좌 실주문으로 확정하기 전까지 **가정값**이다.
> 주문이 사라졌는데 보유가 남으면 `after_hours.py` 가 ERROR 로 남긴다 — 조용히 실패하지는
> 않지만, 확정 전에는 이 탈출을 신뢰하지 말 것.

## 🔴 브로커를 부르는 루프에는 시간 게이트와 백오프가 있어야 한다

`runtime.engine_active_at()` — **KRX 거래일 && 08:50~15:35** 에만 실제 작업을 한다.
그 밖에는 30초 간격으로 잠들고 브로커를 부르지 않는다. 두 창(08:59:30 익일 시가 청산,
15:18~15:28 오버나이트 심사)을 모두 감싼다.

게이트가 없으면 `_control_loop` 이 **초당 코스닥 지수 조회 + 5초마다 후보 스캔** 을
24시간 돌고, `_websocket_loop` 이 실패할 때마다 **1초 간격으로 인증 API 를 무한 재시도**한다.
이는 2026-07-27 실제 사고(pykrx 재로그인 누적으로 KRX 계정 잠김, 하루 158회)와 같은
실패 유형이다 — CLAUDE.md 제약 8번 참고. 재연결은 지수 백오프(1초 → 최대 60초)이고
연결에 성공하면 리셋한다.

## 브로커가 정본이다 — 반환값을 버리지 말 것

취소·청산 호출은 `ReconcileResult` 를 돌려주고 그 안의 `position_quantity` 가 **실제 보유**다.
이걸 버리면 상태기계의 짐작이 현실과 어긋난다.

| 지점 | 버렸을 때 |
|---|---|
| `CANCEL_BUYS` → `cancel_pending_buys()` | 취소와 경합한 부분체결이 `CLOSED` 뒤에 묻혀 **손절·폴백·EOD 어디에도 안 잡힌다**. `machine.adopt_late_fill()` 로 되살린다 |
| `MARKET_SELL` → `sell_actual_position()` | 세션이 `RECONCILING` 에 영원히 남아 슬롯을 잡고, 늦은 청산 손익이 `NULL` 로 남아 **일일 중단선에 안 잡힌다** |

청산은 제출 시점에 체결되지 않는 일이 흔하므로 `tick()` 이 `RECONCILING` 세션도 계속
확인해 보유가 0 이 되면 `CLOSED` 로 닫는다.

## 상태를 놓치면 포지션이 보호 밖으로 나간다

| 경로 | 규칙 |
|---|---|
| 15:18 창 유실 | 15:28 `force_overnight_cap()` 이 `EOD_TRIM` 뿐 아니라 **`LOCKED` 도** 청산한다(`eod_review_missed`). 심사받지 않은 포지션은 오버나이트 자격이 없다 |
| 익일 재시작 | `recover()` 는 `ref_date <= 오늘` 의 **모든 미종료 세션**을 되살린다. 기동일만 보면 전일 오버나이트가 `unknown_position` 으로 밀려 08:59:30 청산 창(30초)에서 빠진다 |
| 시간외 탈출 미체결 | `AFTER_HOURS_EXIT` 도 `overnight_tickers()` 에 포함된다. 빼면 보유분이 하루 더 방치된다 |
| 웹소켓 재연결 | `_subscribed` 는 **연결 단위**다. 연결 성공 시 `clear()` 하지 않으면 재구독을 건너뛰는데 `_feed_connected=True` 라 REST 폴백까지 멈춘다 — 연결은 정상처럼 보이면서 시세 보호가 완전히 없어진다 |

## 청산 원장 — `exit_order_ids`

세션은 청산을 **한 번 이상** 한다(EOD 트림 → 잔여 청산). 브로커의 당일 주문 결과에는
전략 ID 가 없으므로(KIS 는 빈 문자열을 준다) **주문 ID 가 우리 매도를 되찾는 유일한
열쇠**다. 콤마 구분 목록으로 쌓고, `worker._settle_realized_pnl()` 이 전부 합산해
`realized_pnl` 을 기록한다.

- **부분청산은 체결 수량만 대응**시킨다. 미청산분은 미실현이다.
- **미체결 청산은 `0` 이 아니라 `NULL`** 이다. 아직 안 팔린 것을 `0` 으로 적으면 손실이
  일일 한도에서 조용히 사라진다.
- 정산은 `reconcile()` 이 이미 부르는 `get_daily_order_results()` 스냅샷을 재사용한다 —
  브로커 호출이 늘지 않는다.
- **비교 전에 `raw_broker_order_id()` 로 정규화한다.** 감사 ID(`kis:...`)와 브로커 원주문
  ID 는 KIS 에서 절대 같지 않다. MockBroker 는 둘이 같아 **테스트가 이 불일치를 구조적으로
  못 잡는다** — 실제로 이 자리에서 버그가 났다.

## 🔴 "주문을 낼 수 있는가" 와 "진입할 것인가" 는 다른 질문이다

`mode` 하나로 둘을 판단하면 **비상정지가 청산까지 막는다.** 그러면 실제 주식은 남은 채
세션만 `CLOSED` 로 표시되는, 이 시스템에서 가능한 가장 나쁜 상태가 된다 — 사용자가
안전하다고 믿는 순간이 가장 위험해진다.

| 질문 | 판정 | 쓰는 곳 |
|---|---|---|
| 새로 **진입**할 것인가 | `mode is AUTOMATIC` + `guard.can_enter()` | `FIRE_NET` 한 곳뿐 |
| 주문을 **낼 수 있는가** | `service.exits_are_live()` | 손절·취소·EOD·익일청산·시간외 전부 |

`emergency_off()` 는 `mode` 만 끄고 `_orders_enabled` 는 건드리지 않는다. 시간외 잡도
모드가 아니라 `exits_are_live()` 를 본다 — 비상정지 뒤가 그 탈출이 가장 필요한 때다.

## 🔴 상태 전이는 주문보다 먼저 일어난다

`_protective_exit()` 는 인메모리 상태를 `RECONCILING` 으로 바꾼 **뒤** 커맨드를 낸다.
그 사이 브로커 오류가 나면 상태만 바뀌고 주문은 없는데, 상태기계는 `RECONCILING` 에서
중복 청산을 억제하므로 **이후 손절 이벤트가 전부 무시된다.**

`tick()` 이 `RECONCILING` + 보유 > 0 + **열린 주문 0** 을 재제출 신호로 삼는다
(`_retry_stuck_exit`). 열린 주문이 있으면 손대지 않는다 — 그건 정상적인 체결 대기다.

## 취소는 결과를 확인해야 한다

`cancel_open_exits()` 는 `CancelExitsResult(cancelled, stranded)` 를 준다.
**`stranded > 0` 이면 새 매도를 내지 않는다** — 살아 있는 매도 위에 전량매도를 얹으면
보유보다 많이 팔거나 잔량 부족으로 거절된다.

공유 계좌라 취소 대상도 가려야 한다. 브로커의 열린 주문에는 전략 ID 가 없으므로
`order_log` 로 소유자를 확인한다. 다른 전략의 매도는 건드리지 않는다.

## 🔴 브로커 호출은 이벤트 루프에서 실행하지 않는다

모든 `service.*` 호출은 안에서 브로커 HTTP 를 부를 수 있다. 이걸 이벤트 루프에서 그대로
실행하면 **느린 KIS 주문 응답이 웹소켓 수신을 멈춘다** — 시세는 계속 흐르는데 듣는 쪽이
없어서, *다른 종목* 의 손절 틱이 아예 도착하지 않는다.

`runtime._call_service()` 가 호출을 큐에 넣고 `_service_pump` 가 하나씩
`asyncio.to_thread` 로 실행한다.

| 보장 | 이유 |
|---|---|
| **한 번에 하나** | 상태기계가 순서를 요구하고, ORM 세션은 **동시** 접근을 견디지 못한다(순차 크로스 스레드는 괜찮다). 그래서 스캔의 `SecurityMetadata` 조회도 펌프를 거친다 — 이벤트 루프에서 직접 읽으면 주문 처리와 세션을 동시에 만진다 |
| **보호 작업 우선**(`_PRIORITY_HIGH`) | 타이머·지수 래치·피드 상실·EOD 청산이 진입 작업을 앞지른다. 느린 매수 뒤에 매도가 줄 서면 안 된다 |
| **같은 우선순위는 제출 순서** | 시세 이벤트는 순서가 곧 의미다 |
| **예외는 호출자에게** | 펌프가 삼키면 이후 호출이 영영 대기한다 |

> `start()` 의 `recover()` 만 예외다 — 펌프가 아직 없어서 큐에 넣으면 데드락이다.
> 그 시점엔 경합할 상대도 없으므로 직접 `to_thread` 로 돌린다.

> 다른 스레드(FastAPI 관리자 API)는 `runtime.call_threadsafe()` 로만 들어온다.
> 거기서 서비스를 직접 만지면 펌프와 **같은 ORM 세션**에 commit 하게 된다.
>
> 시세 작업은 `_feed_tasks` 로 추적한다. 추적하지 않으면 종료 시 아직 큐에
> 들어가지도 않은 작업이 남은 채 `queue.join()` 이 먼저 끝나고 세션이 닫힌다.
>
> `worker` 에 있던 우선순위 큐(`enqueue_*`/`run_next`)는 **호출자가 없었다.** "매도 우선" 을
> 약속하면서 실제 순서는 이벤트 루프가 정하고 있었으므로 삭제했다. 순서는 위 펌프가 잡는다.

| 대상 | 규칙 |
|---|---|
| EOD 단계 | `eod_stage()` 는 **창이 아니라 하한선**이다. 좁은 창이면 그 몇 분 재시작만으로 상한 미적용 포지션이 익일로 넘어간다. 늦게 시작하면 `force` 로 직행한다(체결 불가능한 트림을 재생하지 않는다) |
| 익일 시가 청산 | 08:59:30 도 하한선이다. 30초 창이면 09:00 직후 재시작이 보유를 하루 방치한다 |
| 미체결 매수 타임아웃 | `recover()` 가 `net_fired_at` 을 복원한다. 안 하면 `on_timer` 가 180초 타임아웃을 영영 못 만난다 |
| 중단된 청산 | `RECONCILING` + 보유 > 0 이면 **재제출**한다. "팔기로 했다" 와 "주문을 보냈다" 사이에서 죽으면 확인만 반복하고 영영 안 판다 |
| 일일 가드 | `limit_up_daily_guard` 테이블에 **직접 저장**한다. 세션 부작용에서 역산하면, 취소할 주문이 없던 코스닥 래치는 흔적이 없어 재시작 때 조용히 풀린다 |
| 코스닥 고점 | 관측할 때마다 저장한다. 재시작 후 다시 쌓으면 이미 떨어진 가격에서 시작해 드로다운이 영영 안 걸린다 |

## 죽은 연결은 끊긴 연결보다 나쁘다

`feed_is_silent()` — 60초 무프레임이면 연결을 버리고 재연결한다. 반쯤 열린 소켓은
`_feed_connected=True` 를 유지해 **REST 폴백까지 막으므로**, 모든 게 정상처럼 보이는 채로
시세 보호가 멈춘다. KIS 는 체결이 없어도 PINGPONG 을 보내므로 완전한 무음은 정상이 아니다.

## 종료 — `to_thread` 는 취소되지 않는다

`stop()` 은 생산자를 먼저 취소하고 **큐를 비운 뒤** 펌프를 끄고 세션을 닫는다.
진행 중인 주문 위에서 세션을 닫으면 브로커 호출이 중간에 끊기고 DB 쓰기가 반쯤 남는다.

## 거래일 경계 — 손익도 가드도 날짜에 매인다

**손익은 발생일에 귀속한다** (`realized_pnl_by_date`, JSON 원장). 오버나이트 보유는 익일
아침에 청산되므로 그 손실은 **익일** 계좌에서 난다 — 진입일에 달면 정작 반응해야 할 날의
중단선이 못 본다. `realized_pnl_total(ref_date)` 는 "그날 장부에 오른" 금액을 합산하며,
세션의 진입일과 무관하다.

> 스냅샷에 있는 날짜만 다시 쓴다. 브로커는 **당일 주문만** 돌려주므로, 전량 덮어쓰면 오늘
> 청산이 체결되는 순간 어제 트림 손익이 원장에서 사라진다.
> `realized_pnl`(총합)은 원장에서 파생한다 — 두 곳에서 따로 계산하면 조용히 어긋난다.

**`DailyGuard` 는 하루짜리다.** `ref_date` 를 들고 있고 날짜가 바뀌면 새로 만든다
(`service._ensure_guard_for`). 두 실패가 여기서 만난다:

| 상황 | 게이트 없으면 |
|---|---|
| 자정을 넘겨 계속 돈 프로세스 | 전일 래치(`feed_disconnected` 등)를 그대로 들고 있어 오늘 거래를 막는다 |
| 장중 재시작 | `attempts`·`pattern_failures`·코스닥 래치가 0 으로 초기화되어 **이미 소진한 제한을 되돌려준다** |

그래서 새 가드는 항상 DB 에서 복원한다(`repository.guard_state`) — 시도 횟수는
`net_fired_at`, 패턴 실패는 `pattern_failure_counted`, 코스닥 래치는
`end_reason == "market_halt"` 가 근거다. 세션 테이블이 이 사실들의 정본이다.

## 멱등 — 같은 이름을 두 번 쓰지 말 것

`repository.transition(action=X)` 은 그 `state_version` 에 이미 이벤트를 남긴다.
worker 가 **같은 action 이름**으로 `event_exists()` 를 검사하면 항상 `True` 가 되어
**주문이 조용히 건너뛰어진다.** 상태 전이와 주문 제출 의도는 서로 다른 action 이름을
써야 한다 (`overnight_trim` vs `overnight_trim_sell`).

## 모드

| 모드 | 동작 |
|---|---|
| `off` | 후보 감시조차 하지 않는다 |
| `recommend_only`(기본) | 종목·가격·수량만 제공. 주문·취소·정정 없음. 실현손익이 없으므로 일일 중단선 합은 항상 0 |
| `automatic` | 동일 신호로 매수·익절·손절·시간청산·미체결 관리를 자동 실행 |

### 🔴 모드와 무관하게 **command worker 를 항상 만든다**

주문 경로는 전부 `mode is AUTOMATIC and worker is not None` 로 막혀 있다(12곳).
`recommend_only` 라고 worker 를 `None` 으로 두면, 나중에 `automatic` 으로 바꿔도
**else 분기(가상 처리)로 빠져 주문이 한 건도 안 나간다** — 예외도 로그도 없이
"켜졌는데 아무것도 안 하는" 상태가 된다. `bootstrap.build_runtime()` 이 모드와
무관하게 worker 를 만드는 이유다. worker 가 있어도 `recommend_only` 에서는 앞쪽 조건이
거짓이라 주문은 절대 나가지 않는다.

### 🔴 `automatic` 은 계좌 전역 실주문 스위치를 다시 통과해야 한다

V1 주문은 스케줄러 `order_cycle` 을 거치지 않는다. 그런데 `MAPS_LIVE_TRADING_ENABLED` 를
강제하는 곳은 **거기 하나뿐**이었다(`scheduler.py` 의 `if live_enabled and not dry_run`).
게이트가 없으면 계좌 전역 스위치가 꺼져 있는데도 V1 이 실주문을 내고,
`_order_log_mode()` 가 같은 스위치를 읽기 때문에 **실거래가 `mock` 으로 기록된다.**

`service.automatic_mode_blocked_reason(settings)` 가 단일 판정이고, 두 경로가 모두 쓴다 —
기동(`bootstrap`)과 **런타임 모드 변경**(`runtime.apply_settings`, API). 기동 시점만 막으면
API 호출 한 번으로 우회된다.

| 차단 사유 | 조건 |
|---|---|
| `live_trading_disabled` | `MAPS_LIVE_TRADING_ENABLED=false` |
| `broker_not_kis` | `MAPS_BROKER_MODE != kis` |
| `real_trading_unconfirmed` | 실계좌인데 `MAPS_CONFIRM_REAL_TRADING` 미설정 |

> **차단 시 `recommend_only` 로 조용히 낮추지 않는다.** 기동을 거부하고(로그) API 는 409 를
> 준다. 요청한 모드로 안 도는데 도는 것처럼 보이는 게 더 나쁘다.

### 모드 전환

| 방법 | 재시작 | 영속 |
|---|---|---|
| `PUT /api/v1/limit-up/settings` | 불필요, 즉시 | ❌ 재시작 시 `.env` 값으로 복귀 |
| `.env` `MAPS_LIMIT_UP_MODE` 변경 | 필요 | ✅ |

API 변경이 재시작에 살아남지 않는 것은 **의도된 안전 방향**이다 — 실수로 켠
`automatic` 이 재부팅으로 부활하면 안 된다. 영구 전환은 명시적 행위여야 한다.

두 실행 방식은 **동일한 신호 엔진**을 쓴다. 자동을 골라도 실거래 스위치·브로커 연결·
위험 한도가 준비되지 않으면 fail-closed 로 주문을 막는다. 시세·호가·체결통보가 끊기면
추천 모드로 완화하지 않고 **신규 주문을 차단**한다.
